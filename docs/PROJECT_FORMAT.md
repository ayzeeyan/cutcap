# CutCap project documents — format 1, core schema 1

`.cutcap` is UTF-8 JSON with `format: "CutCap"`, `format_version: 1`, a complete `project`, and a `sources` manifest. This is the editor's document, not an export. Opening adopts the validated Rust model; saving snapshots that same model. No migration is needed from core schema 1. There was no previously shipped project-file format. Unknown fields, duplicate fields/IDs, future versions and invalid graphs are rejected rather than guessed or partially loaded.

`project` preserves schema, ProjectId, name, rational timeline clock, ordered tracks (identity/name/kind), ordered media references (identity/path/kind) and every existing clip (identity, source/track references, integer start/duration and distinct signed source-in PTS/timebase). Core validates references, positive durations, checked endpoints, kind compatibility and non-overlap. Clip data can be preserved even though clip editing/rendering is not implemented. The UI labels such data as saved clips rather than empty tracks.

`sources` contains exactly one entry per MediaId, with optional validated video-metadata expectations and a full-file SHA-256/byte-length fingerprint. These are document expectations used to detect replacement, **not decoded buffers or a trusted runtime metadata cache**. The engine must re-probe before enabling a reopened video. Core remains filesystem/codec independent. Existing model-only/audio references without video expectations remain in the document but cannot acquire a verified video preview automatically.

Selection, source transport/clock, frame bytes, subprocesses, errors, jobs, synchronization, layout, zoom, session handles and document revision counters are not serialized.

## Paths and source integrity

- Runtime references are absolute. A relative serialized path is explicitly relative to the directory containing the opened `.cutcap` file, never the working directory. Resolve it once off-thread before adoption.
- Save uses a relative path only for a descendant of the destination directory. Other sources remain absolute; no `..` references are generated. Save As computes references from the unchanged runtime sources, so it does not retarget media.
- Reject empty/control-character/over-budget/non-Unicode paths, Windows drive-relative or root-relative references and relative `..`. Project files require an absolute destination ending in `.cutcap`. Unicode/spaces and long Windows paths are tested. The ABI can represent other Windows names, but format 1 explicitly requires Unicode for JSON persistence.
- Existing sources and the destination's parent are canonicalized on workers. Missing references retain their resolved absolute spelling and remain saveable. Absolute Windows references can include the canonical `\\?\` prefix; this is a Windows format, not a cross-platform path translation scheme.
- Moving a project directory with its descendant media works. Moving a project alone does not silently search other directories; the reference becomes Missing. External absolute references continue to identify their original locations.
- Import/verification opens a read handle denying writes/delete/rename on Windows for the duration of FFprobe and the streaming full-file hash (1 MiB scratch buffer, <=32 GiB source). A changed byte, size or incompatible probe result cannot silently replace expectations. No file watcher is implemented: verification occurs on import, reopen and relink, not continuously after a source becomes Ready. A file can change after inspection; decode errors still use the existing failure path.
- After document adoption, the existing single cancellable probe checks one source at a time. Library states are Checking, Ready, Missing, Changed or Unavailable. Saved metadata is shown as context while checking; preview/playback remain unavailable until Ready. A missing file never invalidates the whole project.
- Relink probes/hashes the chosen candidate on that same worker. Only matching original content **and** metadata permits changing the core path. Identity, order and clips remain intact, and a changed path increments the document revision. Changed content must be imported as a new asset; this milestone has no conform/replace-footage semantics. A failed candidate preserves the old reference and a previously usable source. The project menu exposes Relink selected source.

## Save lifecycle and revision correctness

The single Rust command owner captures a validated Project clone plus source expectations and the current document revision. One file operation at a time owns that snapshot on its own worker. Save acceptance is not completion. A nonterminal Updated snapshot shows Saving; a terminal Completed/Failed event releases the pending RequestId. Reliable events never use the ephemeral frame mailbox.

Persistent mutations (track creation, media registration, successful path change) increment the owner revision. Selections, probing, playback, seeking and view serialization do not. Completion records **the snapshot revision**, not whatever revision is current then. Newer edits remain dirty. A new unsaved document is dirty; an opened document begins clean. Save updates the current path only on successful replacement. Failure preserves path, saved revision, live project and the previous valid file.

Open reads/parses/validates on the file worker. It is independent of decoding. Only a complete successful result is adopted by the command owner. It clears transient selection/preview, including reopening the same ProjectId, and then queues source checks. Failed opens preserve the live source, project, selection and dirty state. Project mutations are rejected while Open is in flight; edits may continue during Save. New/Open replacement cannot interrupt an active file operation.

## Filesystem strategy and limits

1. Validate the snapshot, path policy and graph. Reject a destination that identifies referenced source media.
2. Serialize complete bounded bytes. Create an exclusively owned randomly named `.cutcap-*.tmp` in the destination directory using **tempfile 3.27.0**.
3. Write in 64 KiB chunks with cancellation checks. Call `File::sync_all` before replacement.
4. Check cancellation immediately before commit. `NamedTempFile::persist` on the inspected Windows implementation clears the *temporary file's* attribute and calls `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`. There is no destination delete/truncate and no cross-volume copy fallback.
5. Report success after replacement returns. Ordinary errors remove the temp file through RAII; forced process termination can leave an unreferenced temp file, which is never mistaken for a document.

The [tempfile API](https://docs.rs/tempfile/3.27.0/tempfile/struct.NamedTempFile.html#method.persist) documents replacement as atomic; its contents/directory are not synchronized by persist itself. CutCap explicitly syncs the temp contents first. The [Windows operation](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) is a same-directory replacement without `MOVEFILE_COPY_ALLOWED` or `WRITE_THROUGH`. Tests on this machine's local NTFS cover overwrite, sharing-lock failure, cancellation/injected failure before commit, and killing a separate writer process after temp sync but before commit. The previous file remains readable and byte-identical on those failures.

**Limits:** containing-directory metadata is not explicitly flushed on Windows; power loss, storage/controller failures, remote/unusual filesystems, concurrent external writers and a kill *inside* the OS rename were not tested. Existing file ACLs/alternate streams are not preserved as a ReplaceFileW-specific policy; the replacement inherits the new temp file's attributes/security. No universal power-loss durability, history/backup, autosave, external-edit conflict detection or crash recovery is claimed.

Before parsing: regular project file <=16 MiB, bounded read (including growth), JSON nesting <=32, string <=32,768 UTF-8 bytes, <=32 fields/object, <=100,000 elements/array. Typed construction then enforces <=128 tracks, <=128 document media entries, <=100,000 clips, metadata limits and the complete graph. The byte/structure pass precedes typed allocation; limits after deserialization alone would not suffice. These are application resource limits, not an OS sandbox.

## Shutdown

The UI pump and media workers keep their established lifecycle. The project owner does no file I/O. It sleeps on commands when idle and polls completion at <=10 ms while a file job exists. Session destruction drops reliable results first; a file task receives cancellation when the owner drops it. Cancel is checked between chunks and before replacement. An already-entered OS replacement can finish, leaving a complete old or new document, not a partial serialization.

Uninterruptible filesystem calls cannot be bounded by Rust cancellation. Destruction therefore never waits indefinitely for a file task: a task still inside such a call is detached with only its owned snapshot/temp/token, no session/UI reference or ability to adopt state. It cleans up when the OS call returns and cancellation is observed. Source inspection receives cancellation too; destruction waits at most 250 ms for its completion notification, joins completed work, and otherwise detaches the owned probe/hash task. A deterministic blocked-backend test releases it afterward and proves its Windows source handle is released. No forced termination of an OS-stalled thread is claimed. Normal media subprocess cancellation still kills/reaps through the existing adapter. UI close confirmation prevents ordinary user-driven close during a project dialog/file operation and keeps the window responsive. A direct native-session destroy may abandon a request; no terminal delivery after destruction is promised.

Before destructive New/Open or window close, Avalonia offers Save / Don't save / Cancel. Save waits for the accepted request's terminal event and checks the engine's dirty state again; cancellation/failure/newer edits prevent replacement. Dialog Cancel does nothing. File operations use the native asynchronous Windows picker; no filesystem work is done by the view model.
